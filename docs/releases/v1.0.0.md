# Resource Queue Manager — v1.0.0

Resource Queue Manager v1 introduces **multiple independent resource queues**
and a modular scheduling architecture for Home Assistant. Each queue has its
own capacity, strategy, supervised entities, diagnostic sensors and persisted
state. The integration **coordinates reservations only**; Home Assistant
automations remain responsible for controlling equipment.

## What's new

- **Multiple queues** in one integration: create separately named entries,
  each with capacity from 1 to 50 and independent persistent state.
- **Three non-preemptive strategies:**
  - **FIFO:** first waiting request is served first.
  - **LIFO:** most recently queued waiting request is served first.
  - **Priority FIFO:** requests use priority 1–10; ties retain FIFO order.
    Choose `highest_first` or `lowest_first` for each priority queue.
- **Pluggable strategy providers** with separate `provider.py`, `strategy.py`,
  `config.py` and `request.py` contracts.
- **Native Home Assistant forms:** configured queues and strategies are selected
  from the interface; provider-specific fields are validated.
- **Generic supervised entities:** supports Home Assistant domains including
  `switch`, `light`, `fan`, `input_boolean`, `number`, `text`,
  `input_number`, `input_text`, `input_select` and other entities.
- **Domain-aware supervision:** ON/OFF entities must report `off` before an
  active reservation can be released. Other entity types are logical resources
  whose known, available states can be checked; their values do **not** prove a
  physical device is shut off.
- **Explicit multi-queue targeting:** `request`, `release`, `cancel` and
  `resume` accept `config_entry_id`; `request` also accepts optional,
  provider-validated `strategy_data`.
- **Independent recovery:** each queue reloads `paused` and requires an
  explicit `resume` after supervised entities have been checked.
- **French and English interface text** and expanded installation,
  troubleshooting and development documentation.

## Breaking workflow detail for existing users

**When two or more queues are configured, every action call must specify the
owning `config_entry_id`.** Without that field, the integration deliberately
refuses to guess which queue should be modified. Existing single-entry v0.4
calls without `config_entry_id` remain supported while only one queue exists.

Existing v0.4 FIFO configuration entries, legacy sensor identifiers, action
names, persisted active/waiting reservations and entity bindings are retained.
Legacy stored snapshots without strategy/request metadata are supported.
Old queues default to FIFO; changing an algorithm requires an empty queue.

Before upgrading, **back up Home Assistant**, including `.storage` and
automations. Update the old action calls with the original entry ID before
adding another queue. After any restart or reload, inspect the supervised
equipment and resume each queue explicitly.

[Full migration and rollback instructions](https://github.com/HamzaKarfa/Resource-Queue-Manager/blob/v1.0.0/docs/MIGRATION_v0.4_to_v1.md)

## Installation and compatibility

- Requires **Home Assistant 2026.11.0 or newer**.
- Install **Resource Queue Manager** from Home Assistant Marketplace/HACS or
  add the repository: https://github.com/HamzaKarfa/Resource-Queue-Manager
- Restart Home Assistant, then add or configure queue entries under
  **Settings → Devices & services**.
- Each configured entry exposes `active`, `waiting`, `available` and
  `status` sensors; use the actual entity IDs displayed in Home Assistant.

## Known limitations and safety

- Queue reservations do **not** switch devices, measure electrical current,
  enforce global limits across queues or replace independent protection.
- This is **not a certified electrical load-shedding, overcurrent or thermal
  protection system**. Other automations and manual commands can bypass it.
- Priority FIFO does not preempt active bookings. Continuous high-priority
  traffic can starve lower-priority requests (no priority aging).
- A generic `number`, `text`, `sensor` or helper value cannot certify
  physical shutdown. For actuators, supervise an ON/OFF entity and retain
  independent hardware safety provisions.
- Fail-closed recovery can require manual reconciliation of equipment and
  saved reservations after a reboot or interrupted automation.
- Downgrading to v0.4 without restoring the matching pre-upgrade Home Assistant
  backup is **not supported**.

The release is validated by Python and Home Assistant integration tests,
HACS/Marketplace validation and Home Assistant hassfest. Automated tests
simulate entity states and cannot certify real electrical equipment.
