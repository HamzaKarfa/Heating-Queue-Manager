# Resource Queue Manager — v1.0.0

**Prepared release notes — not yet published.**

Resource Queue Manager v1 introduces multiple independent resource queues and a modular strategy system inspired by service providers. It extends the original v0.4 FIFO integration while keeping reservation safety checks and the principle that **user automations control the actual devices**.

## Highlights

- **Multi-instance Home Assistant integration**: configure separate named queue entries, each with its own capacity (1–50), supervised Home Assistant entities (including helpers, native number/text), four diagnostic sensors and persistent state.
- **Three strategies**:
  - **FIFO** — first waiting request receives the next free slot.
  - **LIFO** — newest waiting request receives the next free slot.
  - **Priority FIFO** — orders waiting requests by a priority from 1 to 10; FIFO order breaks ties. Choose `highest_first` or `lowest_first`.
- **Pluggable providers**: each strategy has `provider.py`, `strategy.py`, `config.py` and `request.py`; settings are validated through a common registry and rendered as native Home Assistant selectors.
- **Structured requests**: optional provider-specific `strategy_data` in the common `request` action, persisted separately under `request_data`.
- **Explicit action targeting**: `request`, `release`, `cancel` and `resume` accept `config_entry_id` so actions can safely target a particular queue.
- **Fail-closed recovery** remains per instance. Entries restore `paused` and require manual `resume` after entity-state inspection.
- **Domain-aware supervision** permits native and helper entities while preserving the existing OFF requirement for electrical ON/OFF actuators.

## Upgrade notes — v0.4 users must read

The integration domain and action names remain `resource_queue_manager`. Existing FIFO configuration entries, storage identifiers, reservations, entity bindings and original sensors are preserved. Legacy FIFO snapshots lacking new strategy or request metadata fields remain supported.

**Critical workflow change:** when **more than one queue is configured**, every action must specify the owning `config_entry_id`. Previously valid unqualified calls work only while exactly one entry exists. Update your automations **before** adding a second manager, and filter grant events by `config_entry_id` if you listen to multiple queues.

Priority FIFO requires per-request `strategy_data.priority` (numeric 1–10). A queued request's priority cannot be silently changed by repeating `request`.

Existing active reservations are never preempted, whatever the scheduling strategy. A queue must be empty before changing strategy or strategy-specific configuration. Changing options triggers a reload, leaving the entry `paused` until inspection and explicit `resume`.

**Back up Home Assistant before upgrading**, and follow the complete [migration and rollback guide](../MIGRATION_v0.4_to_v1.md). Do not rely on downgrading a v1-written storage file to v0.4 without restoring the corresponding backup.

## Installation

Requires Home Assistant **2026.11.0+**. Once this release is actually published, use Home Assistant Marketplace or add the GitHub repository link `https://github.com/HamzaKarfa/Resource-Queue-Manager`. Restart Home Assistant and configure each queue under Settings → Devices & services. For a pre-release test, use the full `feat/v1-multi-queue-strategies` component directory in a separate HA test instance instead of the stable Marketplace channel.

See the [README](../../README.md) for setup, action YAML and test automation.

## Safety and limitations

This integration is a **software reservation coordinator**, not a certified power-management or safety device. It does not turn relays ON/OFF or measure current. Manual operations and other automations can bypass the logical capacity. Keep independent electrical and thermal protection.

- Priority FIFO does not preempt active reservations.
- Under continuous higher-priority traffic, lower-priority requests can wait indefinitely (no aging).
- **Any Home Assistant entity domain** can be supervised. `light`, `switch`, `fan` and `input_boolean` retain strict ON/OFF verification before release. Other domains (native/helper number, text, sensors, etc.) are logical resources checked for availability only and are **not evidence of physical shutoff**.
- Each instance has independent capacity; there is no global electrical power limit.
- Restarts and interrupted automations may leave reservations requiring manual reconciliation.
